# Bug fix 2026-05-19: GPT-API silent fallback inflated all win-rates

## TL;DR for the other-server Claude

If you've finished any RL runs from the HP search **before commit
`7d686ec`** (pushed 2026-05-19 ~12:30 KST), the rd 9 / 19 / 29 / 39
win-rate numbers are inflated. **Discard them, `git pull`, and
re-run.** Selectors are unaffected — only Stage-2 RL evals need to
re-run. RL stages take ~16h per run (5 in parallel → ~16h total).

## Symptom

For N=100 sanity check (81212/81312) and the first N=100 HP search,
all eval rounds 9–39 reported **80–96% helpful win-rate** but the
**final round 49 reported 16–30% helpful** under the same checkpoint.
This was attributed earlier to "client_average_z_dict bug at round
49" — that was wrong. The truth was the opposite: **rounds 9–39
were inflated by a silent fallback; round 49 was honest GPT-API**.

## Root cause

In `federatedscope/llm/rlhf/standalone_training.py`, three places
built the test loader for win-rate eval and assigned a `client_id`
to each test prompt via cyclic assignment:

```python
client_id = (idx % num_clients) + 1
```

With `num_clients=100` and 30 test prompts, every `client_id`
landed in `[1, 30]`. Under HH-RLHF's MetaSplitter convention, clients
1–50 are the harmless block and 51–100 are the helpful block — so all
30 test prompts were tagged as harmless-client prompts.

`winrate_metrics._get_winrate_scores_with_gpt_api` filters batches
per metric:
- helpfulness eval: keep only client_ids with `_client_to_cat[cid] == 1`
- harmlessness eval: keep only `_client_to_cat[cid] == 0`

So the helpfulness GPT eval rejected **every** batch, looped to the
iteration cap (1000), returned an empty scores dict, and the caller
silently fell through to `_get_winrate_scores_with_internal_model`.
The internal model has **no category filter** and uses the trained
reward model as the judge — which is biased toward the policy it's
been trained against, hence the inflated 80–96% helpful numbers.

At round 49 a separate code path in standalone_training.py rebuilds
the test loader from `client_test_data` (proper per-client splits)
so all client_ids appear, the GPT-API filter has valid samples, and
the honest scores come through.

## Fix

Commit `7d686ec` adds `_assign_balanced_client_ids` (in
`standalone_training.py`) and uses it at all three test-loader build
sites. It does category-balanced round-robin: for a 30-prompt test
set with `num_clients=100` and `num_cats=2`, the helper assigns 15
prompts to clients in [1, 50] and 15 to [51, 100], evenly distributed
(client_ids 1, 51, 2, 52, 3, 53, ..., 15, 65).

The GPT-API filter now finds 15 valid samples per metric per pass
through the test loader, which is well above the 30-sample eval cap
when combined across two passes.

Verified by smoke test:
```
client_ids: [1, 51, 2, 52, 3, 53, 4, 54, 5, 55, 6, 56, 7, 57, 8, 58,
             9, 59, 10, 60, 11, 61, 12, 62, 13, 63, 14, 64, 15, 65]
harmless (cat 0): 15
helpful  (cat 1): 15
```
