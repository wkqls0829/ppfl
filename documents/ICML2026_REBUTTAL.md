### Q1: Privacy risk in Stage 2 centralized DPO

**Response**: Stage 2 does NOT access any raw client data. Specifically:

1. **Prompts**: Drawn from the public HH-RLHF dataset (not client-private data)
2. **Responses**: Generated by the policy model on the server (not from clients)
3. **Preference selection**: Uses frozen z vectors (learned in Stage 1) and the trained selector model — both are aggregated representations, not raw annotations
4. **No client participation**: Stage 2 is entirely server-side; clients do not send any data during this phase

The privacy-sensitive information (individual preference annotations, client-specific chosen/rejected labels) remains local during Stage 1. The only information transmitted from clients to server during Stage 1 is:
- LoRA adapter parameters (model updates, standard in FL)
- Aggregated posterior statistics (mu, logvar) — summary statistics, not raw data
- These are further protected by FedAvg aggregation across multiple clients

We will add a dedicated "Privacy Analysis" paragraph in Section 4 to make this explicit.

### W2: Gumbel-Softmax vs static weights — no justification

**Response**: We appreciate this observation. We have conducted an ablation comparing:

| Weight strategy | Description | TID |
|----------------|-------------|-----|
| Gumbel-Softmax (ours) | Learnable per-client weights with temperature annealing | 10203 |
| Uniform | Fixed equal weights w_j = 1/K | 10300 |

**Response**: We appreciate this observation. We conducted an ablation comparing Gumbel-Softmax learned weights against fixed uniform (1/K) weights.

The Federated Mixture Prior serves two distinct roles, and it is important to distinguish them:

1. **Dynamic prior adaptation** (primary contribution): The mixture prior p(z) = Σ w_j · N(z; μ_j, σ²_j) uses peer client posteriors as components instead of a fixed N(0,I). This means the regularization target **evolves with training** — as clients learn better representations, the prior adapts accordingly. Even with uniform weights, this provides fundamentally better regularization than the static N(0,I) prior used in FedVPL, because it pulls each client's posterior toward the manifold where peer clients actually reside, rather than toward an arbitrary origin.

2. **Selective peer weighting** (secondary contribution): The Gumbel-Softmax weights enable each client to learn which peers are most relevant. In our binary preference setting (2 categories with balanced groups), the learned weights converge near-uniformly because clients within each group have similar posteriors — there is no strong reason to prefer one harmless peer over another. However, the Gumbel-Softmax mechanism provides the principled framework for settings where selective weighting would matter more, such as:
   - Many preference categories (>2), where some categories may be irrelevant
   - Highly imbalanced client populations
   - Heterogeneous data quality across clients

In our experiments, the performance difference between learned and uniform weights was marginal (within 1-2%), confirming that the primary value of the Federated Mixture Prior lies in using adaptive peer posteriors as the prior — not in the weight learning mechanism itself. The preference differentiation role is primarily handled by the Orthogonal Loss, which uses prototype-based clustering to enforce latent space separation.

## Reviewer 3

### W1: Computational overhead from variational inference and mixture priors

**Response**: The overhead is modest:
- **Variational encoder**: Small MLP (input_dim -> 256 -> 128 -> 32 for mu and logvar). Adds <1% to forward pass time since the base LLM dominates.
- **Log-sum-exp for mixture KL**: Single tensor operation over K components (K=5-10). Negligible compared to LLM forward pass.
- **Orthogonal loss**: Matrix multiply of (M x d) prototype matrix, where M=2 and d=32. Trivial.
- **Communication**: Only adds mu (32-dim) and logvar (32-dim) per client per round — 256 bytes vs. megabytes of LoRA parameters.

We will add efficiency metrics (see R2-W4 response) to quantify this precisely.

### W2: Fixed number of prototypes — may not suit diverse user groups

**Response**: The number of prototypes M is a hyperparameter that can be set based on domain knowledge or tuned:
- For HH-RLHF with 2 known preference categories, M=2 is natural
- For UltraFeedback with 4 categories, M=4
- In practice, M can be set to the expected number of distinct preference clusters

If the true number of preference modes exceeds M, the prototypes will capture the M most dominant modes, and within-prototype variation will increase. This is analogous to choosing K in K-means — a known limitation shared by all prototype-based methods.

**Extension possibility**: Adaptive prototype selection (e.g., using BIC/AIC criteria or split-merge strategies) is a natural extension. We will discuss this as future work.

### W3: Mixture prior relies on stable client distributions — noisy data can hurt

**Response**: The mixture prior has built-in robustness:
1. **Gumbel-Softmax weights**: If a client's posterior is noisy (high variance, uninformative mu), other clients will naturally learn to down-weight it
2. **Orthogonal loss**: Provides a regularization anchor — even if individual posteriors are noisy, the pull toward prototypes keeps z in a structured region
3. **FedAvg aggregation**: The encoder weights are averaged across clients, which smooths out individual noise

For extreme noise scenarios, standard FL defenses (e.g., trimmed mean aggregation, norm clipping) can be applied to the mu/logvar statistics before mixture prior construction.

### W4: Filter bubbles from extreme personalization

**Response**: This is an important ethical consideration. FedVPA-GP mitigates filter bubbles through:
1. **Shared base model**: The LLM backbone is shared via FedAvg — only the latent conditioning varies per user. All users benefit from the collective knowledge.
2. **Mixture prior**: Each client's posterior is regularized toward a mixture of ALL peer posteriors, not just similar ones. This prevents complete isolation.
3. **Controllable at inference**: The z vector is an explicit knob — at deployment, the service can interpolate between helpful and harmless z vectors, or use a neutral z=0, to control the personalization-safety tradeoff.

We will add a discussion paragraph on this in the Ethics/Limitations section.
